# 전체 화면 뷰어 확대 기준 수정 검토

## 문제와 요구 동작

기존 뷰어는 확대율만 변경하고 이미지 이동량은 그대로 두었다.
CSS의 이미지 중앙이 변환 기준이므로 커서 아래나 화면 중앙의 이미지 지점이
확대·축소할 때 움직였다. 이미지를 이동한 뒤에는 도구 모음 확대에서도 발생했다.

휠은 커서 아래 지점을 유지하고, 도구 모음은 현재 뷰어 영역 중앙의 지점을
유지하도록 한다. 화면 맞춤과 이미지 탐색은 기존처럼 배율과 이동을 초기화한다.

## 구현

Lightbox 안의 작은 계산 함수가 새 배율과 기준 좌표에 맞는 이동량을 함께 계산한다.
배율과 이동은 하나의 상태로 관리하고 functional update를 사용해 연속된 native
wheel 이벤트에서도 최신 배율과 이동량을 기준으로 계산한다.

커서 좌표는 현재 뷰어의 bounding rect에서 중앙을 빼서 구한다.
도구 모음은 같은 좌표계의 원점을 기준으로 사용한다.
25~800% 한도를 적용한 실제 배율 비율로 이동량을 보정하며,
한도에 이미 도달했다면 위치를 변경하지 않는다. 세로 이동이 없는 휠은 확대하지 않는다.

드래그는 시작 시점의 이미지 위치 대신 직전 포인터에서의 이동량을 더한다.
따라서 드래그 중 휠 확대 후에도 보정한 위치에서 이동을 이어 간다.
화면 맞춤과 이미지 전환은 드래그 상태도 초기화한다.

기존 passive가 아닌 휠 처리와 배경 스크롤 차단을 유지했다.
새 라이브러리나 범용 뷰어 추상화는 도입하지 않았다.

## 검증

- 수정 전 회귀 테스트에서 커서 기준, 이동 후 커서 기준, 도구 모음 기준,
  연속 휠 기준과 세로 이동 없는 휠 동작의 실패를 확인했다.
- 프런트엔드 전체 테스트 57개 통과. 새 회귀 테스트 8개에는 한도에 도달하는
  순간의 기준점 유지, 한도에서 위치 유지, 드래그 중 확대도 포함한다.
- TypeScript 검사와 production build 통과.
- Python 전체 일반 테스트 184개 및 Ruff 검사 통과.
- diff 공백 검사 통과.
- 실제 WebView2에서 이미지 bounding rect로 기준점의 상대 좌표를 측정했다.
  실제 휠 확대·축소는 커서 아래의 점을 유지했고, 이동량이 생긴 뒤 도구 모음
  확대·축소는 뷰어 중앙의 점을 유지했다.
- 일반 창 1080×900과 작은 창 640×600에서 native 검사를 통과했다.
  배경 스크롤 잠금, 화면 맞춤, 이미지 탐색과 초기화, hover 복원,
  복사·분기 등 기존 검사도 통과했다.

native 결과는 `build/ui-review-bf5010f1/report.json`과
`build/ui-review-af86afdf/report.json`에 있다. 생성 파일은 커밋하지 않는다.
테스트는 별도 화면 밖 창과 합성 이력을 사용했고 클립보드는 복원했다.
실행 중인 앱이나 모델을 변경하지 않았으며 이미지 추론은 실행하지 않았다.
